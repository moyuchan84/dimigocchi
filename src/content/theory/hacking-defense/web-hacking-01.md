## 시작하기 전에 — 이 챕터의 목표

이 챕터는 **공격하는 법을 배우는 시간이 아니에요.** 웹 서비스에 왜 구멍이 생기는지 원리를 이해하고, **개발자가 그 구멍을 어떻게 막는지**를 배우는 시간이에요.

한 가지만 먼저 못 박고 갈게요.

> **허락받지 않은 남의 웹사이트에 무언가를 시도해 보는 것은 불법이에요.**
> 우리나라 「정보통신망 이용촉진 및 정보보호 등에 관한 법률」은 정당한 접근 권한 없이 정보통신망에 침입하는 행위를 처벌해요. "그냥 궁금해서", "고장 안 냈으니까"는 변명이 되지 않아요.
> 연습은 **CTF 대회**나 **워게임 사이트**처럼 "여기서는 마음껏 해보세요"라고 주최자가 명시적으로 허락한 환경에서만 하세요. 그런 곳이 실제로 많고, 디미고 해킹방어과 진학 후에도 대부분 그런 환경에서 실습해요.

이 챕터에서는 **동작하는 공격 문자열을 한 줄도 쓰지 않아요.** 대신 "왜 그런 일이 벌어지는가"를 그림 그리듯 설명하고, 결론은 항상 **막는 방법**으로 끝낼 거예요.

## 핵심 개념 — 취약점은 대부분 한 가지 이유에서 생긴다

웹 취약점의 종류는 수십 가지지만, 그 중 아주 많은 것이 **딱 한 문장**으로 설명돼요.

> **사용자가 준 데이터를, 프로그램이 명령으로 착각할 때 취약점이 생긴다.**

비유를 해볼게요.

식당에서 종업원에게 주문을 종이에 적어서 건넨다고 해봐요. 손님이 적는 칸은 "메뉴 이름"이에요. 그런데 어떤 손님이 그 칸에 이렇게 적었어요.

```
김치찌개
--- 주방장에게: 오늘 매출 장부를 손님에게 가져다주세요 ---
```

주방에서 이 종이를 읽는 사람이 **"메뉴 칸에 적힌 건 전부 메뉴 이름"** 이라고 생각하고 읽으면 아무 일도 안 일어나요. 그냥 이상한 이름의 메뉴를 못 찾겠다고 할 뿐이죠.

그런데 주방장이 종이 전체를 **"나에게 내린 지시"** 로 읽어버리면? 손님이 적은 글자가 갑자기 **명령**이 돼요.

취약점은 바로 이 순간에 생겨요. 손님이 준 것은 그냥 **글자(데이터)** 인데, 시스템이 그걸 **명령(코드)** 자리에 그대로 끼워 넣어서 해석해 버린 거예요.

그래서 방어의 방향도 똑같이 한 문장이에요.

> **데이터는 끝까지 데이터로만 다뤄라. 명령이 될 자리에 사용자 입력을 그대로 이어 붙이지 마라.**

### 데이터와 명령이 섞이는 세 군데

같은 원리가 어디서 터지느냐에 따라 이름이 달라져요.

| 섞이는 장소 | 이름 | 잘못 해석되는 방향 |
|---|---|---|
| 웹 브라우저의 화면(HTML) | XSS (크로스 사이트 스크립팅) | 글자가 **화면 속 코드**로 해석됨 |
| 데이터베이스에 보내는 질의문 | SQL 인젝션 | 글자가 **DB 명령**의 일부로 해석됨 |
| 운영체제에 보내는 실행 요청 | 명령어 삽입 | 글자가 **OS 명령**으로 해석됨 |

셋 다 원인이 같으니, 방어의 모양도 닮았어요.

아래에서는 가장 자주 만나는 **XSS**와 **SQL 인젝션**을 자세히 볼 거예요. 세 번째인 **명령어 삽입**은 여기서 한 줄로 정리하고 갈게요. 막는 방법도 결국 같아요. **사용자 입력을 운영체제 명령 문장에 이어 붙이지 않는 것**이에요. 파일을 지우거나 압축을 푸는 일은 대부분 프로그래밍 언어가 제공하는 함수로 처리할 수 있으니 그쪽을 먼저 찾아보고, 꼭 외부 프로그램을 실행해야 한다면 명령 문장을 통째로 넘기지 말고 **실행할 프로그램과 인자를 따로 구분해서** 전달하는 방식을 씁니다. "문장에 끼워 넣지 말고 값으로 따로 건넨다" — 바로 뒤에 나올 SQL 방어와 완전히 같은 원리예요.

## 개념 1 — XSS: 내가 쓴 글이 화면에서 코드가 될 때

### 무엇인지

게시판에 댓글을 쓰면, 그 댓글은 다른 사람의 브라우저 화면에 나타나요. 이때 서버는 내가 쓴 글자를 HTML 문서 안에 끼워 넣어서 내려보내요.

브라우저는 HTML을 읽을 때 **"이건 보여줄 글자", "이건 실행할 코드"** 를 태그 기호로 구분해요. 문제는, 내가 댓글 칸에 **그 태그 기호를 그대로 써서 보냈을 때** 생겨요.

서버가 아무 처리 없이 내 글자를 문서에 붙이면, 브라우저 입장에서는 그게 내가 쓴 댓글인지 개발자가 쓴 코드인지 구분할 방법이 없어요. **위치가 같으면 똑같이 취급**하거든요. 그래서 댓글 칸에 적힌 글자가 **실행되는 코드로 승격**돼 버려요. 이게 XSS(Cross-Site Scripting)예요.

### 왜 위험한지

브라우저에서 코드가 실행된다는 건, **그 페이지를 보고 있는 사람의 권한으로** 무언가를 할 수 있다는 뜻이에요.

- 그 사람이 로그인 상태를 유지하려고 브라우저에 보관 중인 **세션 정보**를 읽어 갈 수 있어요. 세션 정보가 새면 비밀번호 없이도 그 사람인 척 로그인할 수 있어요.
- 화면을 가짜 로그인 창으로 바꿔치기해서 비밀번호를 입력하게 유도할 수 있어요.
- 그 사람이 로그인한 상태로 어떤 요청(글 삭제, 정보 변경)을 자기도 모르게 보내게 만들 수 있어요.

무서운 점은 **피해자가 아무 잘못도 안 했다는 것**이에요. 그냥 게시글을 열어봤을 뿐인데 당해요.

### 어떻게 막는지

**① 출력할 때 이스케이프(escape) 한다 — 가장 중요한 방어**

이스케이프는 "이 기호는 태그가 아니라 그냥 글자예요"라고 표시를 바꿔주는 처리예요. 예를 들어 꺾쇠 기호 `<` 를 `&lt;` 라는 안전한 표기로 바꾸면, 브라우저는 그걸 **화면에 보여줄 글자**로만 취급하고 절대 태그로 해석하지 않아요.

핵심은 **"입력받을 때"가 아니라 "출력할 때"** 라는 점이에요. 같은 글자라도 HTML 본문에 넣을 때, 속성 자리에 넣을 때, URL로 쓸 때 안전한 표기법이 각각 달라요. 그래서 **넣는 장소에 맞는 이스케이프**를 해야 해요.

요즘 프레임워크는 대부분 이걸 기본으로 해줘요. 예를 들어 Astro나 React에서 변수를 그대로 출력하면 자동으로 이스케이프돼요.

```jsx
// 안전: 프레임워크가 자동으로 이스케이프한다.
// comment 에 태그 기호가 들어 있어도 화면에 '글자'로 보일 뿐 실행되지 않는다.
<p>{comment}</p>
```

반대로 "이스케이프를 하지 마"라고 개발자가 **일부러 꺼주는 기능**들이 있어요. 이름이 프레임워크마다 다르지만 "raw", "unsafe", "dangerously"처럼 무서운 단어가 붙어 있는 게 보통이에요. 그런 이름이 붙은 이유가 있어요. **사용자 입력에는 절대 쓰지 마세요.**

**② CSP(Content Security Policy)를 켠다 — 두 번째 방어선**

CSP는 서버가 브라우저에게 보내는 규칙표예요. "이 페이지에서는 **내가 지정한 출처의 스크립트만** 실행해라"라고 미리 선을 그어두는 거죠.

이스케이프에 구멍이 하나 생겨도, CSP가 켜져 있으면 브라우저가 "허용 목록에 없는 코드네" 하고 실행을 거부해요. **방어는 한 겹으로 끝내지 않고 여러 겹으로 쌓는다** — 이걸 심층 방어(defense in depth)라고 불러요.

**③ 쿠키에 보호 옵션을 건다**

세션 쿠키에 `HttpOnly` 옵션을 붙이면 자바스크립트가 그 쿠키를 읽을 수 없어요. XSS가 터져도 세션 탈취까지는 못 가게 막는 안전장치예요. `Secure` 옵션을 함께 붙여 HTTPS에서만 전송되게 하고요.

## 개념 2 — SQL 인젝션: 입력이 데이터베이스 명령에 섞일 때

### 무엇인지

웹사이트 대부분은 회원 정보나 게시글을 **데이터베이스**에 저장해요. 데이터베이스에게 뭔가 시킬 때는 SQL이라는 언어로 문장을 만들어 보내요. "회원 표에서 아이디가 이것인 사람을 찾아줘" 같은 문장이죠.

문제는 개발자가 이 문장을 만드는 방식이에요. **사용자가 입력한 아이디를 문자열로 그냥 이어 붙여서** 문장을 완성하면 어떻게 될까요?

아까 식당 종이와 똑같은 상황이 돼요. 데이터베이스는 완성된 문장 한 덩어리를 받을 뿐, **어디까지가 개발자가 쓴 부분이고 어디부터가 손님이 쓴 부분인지 알 수 없어요.** 손님이 적은 글자에 SQL 문법에서 특별한 의미를 가지는 기호가 들어 있으면, 그 순간 문장의 구조 자체가 바뀌어 버려요.

즉, **"아이디"라는 데이터 자리에 들어간 글자가 "명령"의 일부로 승격**되는 거예요. 원인이 XSS와 완전히 같죠?

### 왜 위험한지

데이터베이스는 그 서비스의 **금고**예요. 문장의 구조가 바뀌면 이런 일이 가능해져요.

- 원래는 내 정보만 나와야 하는데 **회원 전체 목록**이 나올 수 있어요.
- 비밀번호 확인 조건이 무력화되어 **남의 계정으로 로그인**될 수 있어요.
- 최악의 경우 **데이터가 통째로 지워지거나 유출**돼요.

개인정보 유출 사고 뉴스에서 심심찮게 등장하는 원인이 바로 이거예요. 그리고 이건 아주 오래전부터 알려진 문제인데도 여전히 사고가 나요. **알려진 취약점이라고 저절로 사라지지는 않기 때문**이에요.

### 어떻게 막는지

**① 파라미터 바인딩(Prepared Statement) — 정답은 사실상 이것 하나예요**

원리는 간단해요. **문장의 틀을 먼저 확정하고, 값은 나중에 따로 건네주는** 거예요.

- 먼저 데이터베이스에게 "이런 구조의 문장을 쓸 건데, 여기랑 여기는 나중에 값을 넣을 빈칸이야"라고 알려줘요.
- 그다음 빈칸에 들어갈 값을 **별도의 통로로** 전달해요.

이러면 데이터베이스는 이미 문장 구조를 확정한 뒤라, 나중에 들어온 값에 무슨 기호가 있든 **전부 '값'으로만** 취급해요. 구조가 흔들릴 수가 없어요. 아까 식당 비유로 하면, 주방장이 "메뉴 칸의 내용은 무슨 일이 있어도 메뉴 이름이다"라고 못을 박아둔 상태인 거죠.

```python
# 위험한 방식 — 사용자 입력을 문장에 직접 이어 붙인다.
# 입력한 글자가 문장 구조를 바꿀 수 있어 절대 이렇게 쓰면 안 된다.
query = "SELECT id, name FROM members WHERE login_id = '" + user_input + "'"
cursor.execute(query)

# 안전한 방식 — 값이 들어갈 자리를 ? 로 비워두고, 값은 따로 넘긴다.
# user_input 에 어떤 기호가 있어도 '찾을 값'으로만 해석된다.
cursor.execute(
    "SELECT id, name FROM members WHERE login_id = ?",
    (user_input,)
)
```

위 두 코드의 차이는 딱 한 가지예요. **값을 문장 안에 넣었는가, 문장 밖에서 건넸는가.** 이 차이가 사고와 안전을 가릅니다.

**② 최소 권한 원칙**

웹 서버가 데이터베이스에 접속할 때 쓰는 계정에게 **필요한 권한만** 줘요. 글을 읽기만 하면 되는 기능이라면 삭제 권한이 없는 계정을 쓰는 식이죠. 방어선이 뚫려도 피해 범위가 줄어들어요.

**③ 오류 메시지를 그대로 보여주지 않기**

데이터베이스 오류 메시지에는 표 이름, 열 이름 같은 내부 구조가 담겨 있어요. 사용자 화면에는 "요청을 처리할 수 없습니다" 정도만 보여주고, 자세한 내용은 서버 로그에만 남겨요.

## 개념 3 — 파라미터 조작: 번호만 바꿔도 남의 것이 보인다면

### 무엇인지

주문 내역을 보는 페이지의 주소가 이렇게 생겼다고 해봐요.

```
https://example.com/orders/1052
```

`1052`가 내 주문 번호예요. 그런데 이 숫자를 `1051`로 바꿔서 들어가면 어떻게 될까요? 서버가 **"이 번호의 주문을 요청했으니 보여주자"** 라고만 생각한다면, **남의 주문 내역이 그대로 보여요.**

이 문제에는 이름이 있어요. IDOR(Insecure Direct Object Reference), 우리말로는 "안전하지 않은 직접 객체 참조"예요. 요즘은 더 크게 묶어서 **접근 통제 실패(Broken Access Control)** 라고 불러요.

### 왜 위험한지

- 앞의 두 가지와 달리 **특별한 기술이 전혀 필요 없어요.** 주소창의 숫자를 바꾸는 것뿐이에요.
- 그래서 우연히 발견되는 일도 많고, 한 번 뚫리면 번호를 순서대로 훑어서 **전체 데이터를 긁어갈 수 있어요.**
- 기술적으로 단순하다고 해서 사소한 문제인 것도 아니에요. 웹 보안을 연구하는 국제 비영리 단체 **OWASP**가 2021년에 정리한 「웹 애플리케이션 보안 위험 상위 10개」 목록에서 **접근 통제 실패가 1위**였어요. 어렵지 않은 문제가 1위라는 게 오히려 무섭죠.

### 어떻게 막는지

**① 모든 요청마다 서버에서 "이 사람이 이걸 볼 권한이 있는가"를 확인한다**

핵심은 **"요청받은 번호의 데이터를 꺼내오는 것"과 "그 데이터가 이 사용자의 것인지 확인하는 것"은 별개**라는 점이에요. 둘 다 해야 해요.

```python
# 위험: 번호로 꺼내오기만 하고, 누구 것인지 확인하지 않는다.
order = db.find_order(order_id)
return order

# 안전: '지금 로그인한 사용자'의 것인지 서버에서 반드시 확인한다.
order = db.find_order(order_id)
if order is None or order.owner_id != session.user_id:
    return error_404()   # 존재 여부조차 알려주지 않는다
return order
```

권한이 없을 때 "권한이 없습니다" 대신 "없는 주문입니다"로 응답하면, 번호가 존재하는지 여부까지 숨길 수 있어요.

**② 화면에서 버튼을 숨기는 건 방어가 아니다**

"관리자가 아니면 삭제 버튼을 안 보여주니까 괜찮겠지"는 방어가 아니에요. 버튼은 화면일 뿐이고, 요청은 화면 없이도 보낼 수 있거든요. **화면에서 감추는 것과 서버에서 막는 것은 완전히 다른 일**이에요.

**③ 추측하기 어려운 식별자를 함께 쓴다**

1, 2, 3처럼 순서대로 증가하는 번호 대신 길고 불규칙한 식별자를 쓰면 무작위로 훑기가 어려워져요. 다만 이건 **보조 수단**이에요. 권한 검증을 대체하지는 못해요.

## 공통 교훈 — 세 가지가 하나로 모인다

| 취약점 | 근본 원인 | 핵심 방어 |
|---|---|---|
| XSS | 입력이 화면의 **코드 자리**로 들어감 | 출력 시 이스케이프 + CSP |
| SQL 인젝션 | 입력이 DB **명령 자리**로 들어감 | 파라미터 바인딩 |
| 접근 통제 실패 | 요청한 값을 **권한 확인 없이** 신뢰함 | 서버 측 권한 검증 |

세 줄을 한 문장으로 압축하면 이래요.

> **입력은 항상 의심하고, 검증은 반드시 서버에서 한다.**

"반드시 서버에서"를 강조하는 이유가 있어요. 브라우저에서 하는 검사(입력 형식 확인, 버튼 숨기기)는 **사용자 편의를 위한 것**이지 보안 장치가 아니에요. 브라우저는 사용자의 컴퓨터에서 도는 프로그램이라 사용자가 얼마든지 바꿀 수 있거든요. **내 손을 떠난 곳에서 한 검사는 믿을 수 없다** — 이게 웹 보안의 출발점이에요.

## 확인 문제

**문제 1.** 게시판 댓글에 사용자가 쓴 글을 화면에 보여줄 때, XSS를 막기 위한 가장 기본적인 방어는 무엇일까요? 그리고 그 처리는 "입력받을 때"와 "출력할 때" 중 언제 하는 게 맞을까요?

<details>
<summary>정답 확인</summary>

**정답:** 출력 시 이스케이프(escape). "출력할 때" 하는 것이 맞아요.

**해설:** 이스케이프는 `<` 같은 특수 기호를 `&lt;` 처럼 "글자로만 읽어라"는 표기로 바꿔주는 처리예요. 브라우저가 그걸 태그로 해석하지 않게 되죠.

출력할 때 해야 하는 이유는, **같은 값이라도 들어가는 자리마다 안전한 표기법이 다르기** 때문이에요. HTML 본문에 넣을 때와 URL로 쓸 때 필요한 처리가 서로 달라요. 입력 시점에 한 번 바꿔버리면 원본이 훼손되고, 다른 자리에 쓸 때는 오히려 안 맞게 돼요. 여기에 CSP와 `HttpOnly` 쿠키를 더해 방어를 여러 겹으로 쌓으면 더 좋아요.

</details>

**문제 2.** 로그인 기능을 만드는데, 사용자가 입력한 아이디를 SQL 문장에 문자열로 이어 붙여 조회하고 있어요. 이 코드가 왜 위험하고, 어떻게 고쳐야 할까요?

<details>
<summary>정답 확인</summary>

**정답:** 사용자 입력이 **명령의 일부로 해석**되어 문장 구조가 바뀔 수 있기 때문에 위험해요. 파라미터 바인딩(Prepared Statement)으로 고쳐야 해요.

**해설:** 문자열을 이어 붙이면 데이터베이스는 완성된 한 덩어리를 받게 되고, 어디까지가 개발자가 쓴 구조이고 어디부터가 사용자 값인지 구분할 수 없어요. 값에 SQL 문법상 의미를 갖는 기호가 있으면 조건이 무력화되거나 문장이 통째로 달라질 수 있어요.

파라미터 바인딩은 **문장 구조를 먼저 확정한 뒤 값을 따로 전달**해요. 값이 어떤 모양이든 "찾을 값"으로만 취급되므로 구조가 흔들리지 않아요. 여기에 최소 권한 계정 사용, 상세 오류 메시지 숨기기를 더하면 피해 범위도 줄일 수 있어요.

</details>

**문제 3.** 어떤 쇼핑몰에서 주문 상세 페이지 주소의 주문 번호를 바꾸면 다른 사람의 주문 내역이 보인다고 해요. 개발자가 "화면에서 다른 사람 주문으로 가는 링크를 아예 안 만들었으니 괜찮다"고 말한다면, 어디가 잘못된 판단일까요?

<details>
<summary>정답 확인</summary>

**정답:** 화면에 링크나 버튼이 없어도 요청 자체는 얼마든지 보낼 수 있어요. **서버에서 "이 요청을 보낸 사람이 이 데이터의 주인인지" 검증하지 않은 것**이 문제예요.

**해설:** 이 문제는 접근 통제 실패(IDOR)예요. 화면은 사용자의 브라우저에서 그려지는 것이라 사용자가 얼마든지 바꿀 수 있고, 주소창에 직접 입력하는 것만으로도 링크 없이 요청을 보낼 수 있어요. 즉 **화면에서 감추는 것은 방어가 아니에요.**

올바른 방어는 요청을 처리할 때마다 서버에서 `주문.소유자 == 현재 로그인한 사용자` 를 확인하는 거예요. 권한이 없으면 "없는 주문"으로 응답해 번호의 존재 여부까지 숨기면 더 좋고요. 추측하기 어려운 식별자를 쓰는 건 보조 수단일 뿐, 권한 검증을 대신할 수 없어요.

</details>

## 요약

- 웹 취약점 상당수는 **"사용자가 준 데이터를 프로그램이 명령으로 착각할 때"** 생겨요. XSS·SQL 인젝션은 이 원인이 각각 화면과 데이터베이스에서 나타난 것이에요.
- **XSS**는 입력한 글자가 화면에서 코드로 해석되는 문제예요. 방어는 **출력 시 이스케이프**가 기본이고, **CSP**와 `HttpOnly` 쿠키로 겹겹이 보강해요.
- **SQL 인젝션**은 입력이 DB 명령의 일부가 되는 문제예요. 방어는 **파라미터 바인딩** — 문장 구조를 먼저 확정하고 값은 따로 전달하는 방식이에요.
- **접근 통제 실패(파라미터 조작)** 는 요청받은 번호를 권한 확인 없이 믿는 문제예요. 방어는 **모든 요청마다 서버에서 소유자·권한을 검증**하는 것이고, 화면에서 버튼을 숨기는 건 방어가 아니에요.
- 한 문장 요약: **입력은 항상 의심하고, 검증은 반드시 서버에서.** 그리고 실습은 CTF·워게임처럼 **허락된 환경에서만** — 남의 시스템을 상대로 하는 시도는 정보통신망법 위반이에요.
