## 핵심 개념 — 네트워크는 왜 "계층"으로 나눌까

친구에게 택배를 보낸다고 생각해 봐요. 여러분이 하는 일은 물건을 상자에 넣고, 주소를 적고, 택배 기사님께 맡기는 것까지예요. 그 상자가 트럭에 실리는지 비행기에 실리는지, 어느 물류 창고를 거치는지는 몰라도 되죠. 반대로 택배 기사님은 상자 **안에 뭐가 들었는지** 몰라도 배달할 수 있어요.

이렇게 **각자 자기 할 일만 하고, 위아래 단계의 사정은 몰라도 되게** 역할을 나눠 쌓아 올린 구조를 네트워크에서는 **계층(layer)**이라고 불러요. 계층으로 나누면 좋은 점이 명확해요.

- 문제가 생겼을 때 **어느 층이 문제인지** 좁혀서 찾을 수 있어요. (인터넷이 안 될 때 "랜선이 빠졌나? IP가 잘못됐나? 사이트가 죽었나?"를 순서대로 확인하는 게 바로 이거예요)
- 한 층을 통째로 바꿔도 다른 층은 그대로 쓸 수 있어요. 와이파이든 랜선이든 유튜브는 똑같이 나오죠.
- 회사마다 장비를 다르게 만들어도 **약속(프로토콜)**만 지키면 서로 통신할 수 있어요.

여기서 **프로토콜(protocol)**은 "통신할 때 지키기로 한 약속"이에요. 전화를 받으면 "여보세요"라고 말하는 것도 일종의 프로토콜이죠.

## OSI 7계층 한 층씩 보기

국제표준화기구(ISO)가 만든 참조 모델이 **OSI 7계층**이에요. 실제 인터넷이 이대로 구현돼 있다기보다는, **네트워크를 설명하고 문제를 나눠 보기 위한 지도**에 가까워요. 아래에서 위로 올라가며 봐요.

| 계층 | 이름 | 하는 일 | 대표 예 |
|---|---|---|---|
| 7 | 응용 계층 | 사람이 쓰는 프로그램과 직접 맞닿는 층 | HTTP, DNS, SMTP |
| 6 | 표현 계층 | 문자 인코딩, 압축, 암호화 형식 변환 | UTF-8, JPEG |
| 5 | 세션 계층 | 대화의 시작·유지·종료 관리 | 연결 세션 관리 |
| 4 | 전송 계층 | 어느 **프로그램**에게 줄지, 제대로 갔는지 책임 | TCP, UDP, 포트 |
| 3 | 네트워크 계층 | 어느 **컴퓨터**로 갈지 길 찾기 | IP, 라우터 |
| 2 | 데이터 링크 계층 | **바로 옆 장비**까지 안전하게 전달 | 이더넷, MAC 주소, 스위치 |
| 1 | 물리 계층 | 실제 전기·빛·전파 신호로 바꾸기 | 랜선, 광케이블, 전파 |

각 층을 한 문장으로 다시 정리하면 이래요.

- **1계층 물리**: 0과 1을 실제 신호로 바꿔 선이나 공기 중으로 보내요. 랜선이 빠져 있으면 여기서부터 막힌 거예요.
- **2계층 데이터 링크**: 같은 네트워크 안에서 **바로 옆 장비**까지 전달해요. 장비마다 공장에서 새겨진 고유 번호인 **MAC 주소**를 써요.
- **3계층 네트워크**: 전 세계 어디든 갈 수 있게 **IP 주소**로 목적지를 찾고, 라우터가 다음에 어디로 넘길지 정해요. 택배의 "주소지 배정"에 해당해요.
- **4계층 전송**: 컴퓨터에 도착한 데이터를 **어느 프로그램**에게 줄지 **포트 번호**로 구분하고, 빠짐없이 순서대로 도착했는지 챙겨요.
- **5·6·7계층**: 실제 인터넷에서는 뚜렷이 나뉘지 않고 프로그램 안에서 함께 처리되는 경우가 많아요. 그래서 아래 TCP/IP 모델에서는 하나로 합쳐 버려요.

데이터가 위에서 아래로 내려갈 때는 층마다 **앞에 자기 정보를 덧붙여요**. 이걸 **캡슐화(encapsulation)**라고 해요. 선물을 상자에 넣고, 그 상자를 포장지로 싸고, 다시 택배 봉투에 넣는 것과 똑같아요. 받는 쪽은 아래에서 위로 올라가며 하나씩 뜯어서 원래 데이터를 꺼내요.

```text
[ 보내는 쪽 ]                       [ 받는 쪽 ]
7 응용    데이터                      데이터
4 전송    [TCP헤더|데이터]     ↑      [TCP헤더|데이터]
3 네트워크 [IP|TCP헤더|데이터]  ↑      [IP|TCP헤더|데이터]
2 링크    [이더넷|IP|TCP|데이터]      [이더넷|IP|TCP|데이터]
1 물리     ─────  신호  ─────→  ─────  신호  ─────
```

## TCP/IP 4계층과의 대응

OSI가 "이론상의 지도"라면, 실제 인터넷이 돌아가는 방식을 정리한 건 **TCP/IP 모델**이에요. 층이 4개로 더 단순해요.

| TCP/IP 4계층 | 대응하는 OSI 계층 | 대표 프로토콜 |
|---|---|---|
| 응용 계층 | 7 + 6 + 5 | HTTP, HTTPS, DNS, SMTP, FTP |
| 전송 계층 | 4 | TCP, UDP |
| 인터넷 계층 | 3 | IP, ICMP |
| 네트워크 접근 계층 | 2 + 1 | 이더넷, 와이파이 |

OSI의 5·6·7이 TCP/IP에서는 **응용 계층 하나로 합쳐진다**는 점, 1·2가 **네트워크 접근 계층 하나로 합쳐진다**는 점만 확실히 기억하면 돼요. 시험에서 대응 관계를 묻는 문제가 자주 나와요.

## IP 주소와 포트 — 건물 주소와 방 번호

- **IP 주소**는 네트워크에서 **컴퓨터(장비)를 찾는 주소**예요. `192.168.0.10`처럼 점으로 나뉜 네 덩어리로 쓰는 것이 IPv4예요. 각 덩어리는 0~255 사이의 값이에요.
- **포트 번호**는 그 컴퓨터 안에서 **어느 프로그램에게 줄지** 가리키는 번호예요. 0부터 65535까지 있어요.

아파트에 비유하면 **IP 주소는 동 주소, 포트는 호수**예요. 주소만 알면 건물까지는 가지만, 몇 호인지 알아야 문 앞에 도착하죠. 한 컴퓨터에서 웹 브라우저도 켜고 게임도 켜고 메신저도 켜 두는데 서로 데이터가 섞이지 않는 이유가 바로 포트예요.

자주 쓰이는 포트는 미리 약속돼 있어요. 이런 걸 **잘 알려진 포트(well-known port)**라고 해요.

| 포트 | 프로토콜 | 용도 |
|---|---|---|
| 22 | SSH | 원격 접속(암호화) |
| 53 | DNS | 도메인 이름을 IP로 바꾸기 |
| 80 | HTTP | 웹(암호화 없음) |
| 443 | HTTPS | 웹(암호화) |

그리고 **도메인 이름**(`www.example.com`)은 사람이 외우기 쉬우라고 붙인 별명이에요. 실제 통신은 IP 주소로 하기 때문에, 이름을 IP로 바꿔 주는 **전화번호부 역할**을 하는 것이 **DNS**예요.

## TCP와 UDP — 등기우편과 엽서

전송 계층에는 성격이 아주 다른 두 프로토콜이 있어요.

| 비교 | TCP | UDP |
|---|---|---|
| 연결 | 먼저 연결을 맺고 시작 | 연결 없이 바로 보냄 |
| 신뢰성 | 도착 확인·재전송·순서 보장 | 보장하지 않음 |
| 속도 | 상대적으로 느림 | 빠르고 가벼움 |
| 비유 | 등기우편 | 엽서 |
| 쓰는 곳 | 웹, 메일, 파일 전송 | 실시간 영상·음성, 게임, DNS |

TCP는 통신을 시작하기 전에 **3-웨이 핸드셰이크**라는 인사를 세 번 주고받아요. "연결할까?(SYN)" → "좋아, 나도 연결할게(SYN+ACK)" → "확인했어(ACK)" 순서예요. 전화를 걸어 "여보세요" → "네, 여보세요" → "아, 저 OO인데요"로 시작하는 것과 똑같아요.

여기서 중요한 감각 하나. **느린 게 나쁜 게 아니라 용도가 다른 거예요.** 파일을 받는데 중간이 한 조각 빠지면 파일이 깨지니 TCP가 맞아요. 반대로 화상통화에서 0.5초 전 목소리를 재전송받아 봐야 이미 늦었으니, 조금 끊기더라도 계속 흘려보내는 UDP가 맞고요.

## HTTP 요청과 응답의 구조

웹에서 브라우저와 서버가 대화하는 약속이 **HTTP**예요. 구조는 아주 단순해서, **요청 한 번에 응답 한 번**이 오가요.

요청은 이렇게 생겼어요.

```http
GET /guide/schedule HTTP/1.1
Host: dimigocchi.vercel.app
User-Agent: Mozilla/5.0
Accept: text/html
```

- 첫 줄: **메서드 + 경로 + 버전**
- 그 아래: **헤더**들. `이름: 값` 형태로 부가 정보를 담아요
- POST처럼 보낼 내용이 있으면 빈 줄 하나를 두고 **본문(body)**이 이어져요

응답은 이렇게 생겼어요.

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1024

<html> ... 페이지 내용 ... </html>
```

**주요 메서드**는 "무엇을 하려는가"를 나타내요.

| 메서드 | 뜻 |
|---|---|
| GET | 자료를 달라 (주소창에 입력하면 대부분 이것) |
| POST | 자료를 보낸다 (글쓰기, 로그인 등) |
| PUT | 자료를 통째로 바꾼다 |
| DELETE | 자료를 지운다 |

**상태 코드**는 세 자리 숫자인데, **맨 앞자리만 봐도 성격이 보여요.**

| 범위 | 의미 | 예 |
|---|---|---|
| 2xx | 성공 | 200 OK |
| 3xx | 다른 곳으로 이동 | 301 영구 이동, 302 임시 이동 |
| 4xx | **요청한 쪽** 잘못 | 400 잘못된 요청, 403 권한 없음, 404 없는 주소 |
| 5xx | **서버** 잘못 | 500 서버 내부 오류, 503 서비스 불가 |

404를 자주 보니까 익숙하죠. 4로 시작하니 "내가 주소를 잘못 쳤구나", 500번대가 뜨면 "내 잘못이 아니라 서버가 아픈 거구나"로 읽으면 돼요.

마지막으로 **HTTPS**는 HTTP에 암호화를 씌운 거예요. 주고받는 내용을 중간에서 읽지 못하게 만들어 **기밀성**을, 내용이 바뀌지 않았음을 확인해 **무결성**을 지켜 줘요. 요즘 브라우저가 `http://` 사이트에 "안전하지 않음"이라고 표시하는 이유예요.

## 예시 — 주소창에 입력하면 무슨 일이 벌어질까

`https://dimigocchi.vercel.app` 를 입력하고 엔터를 쳤을 때 벌어지는 일을 계층과 함께 따라가 봐요.

1. **DNS 조회 (응용 계층)** — 브라우저가 "이 도메인의 IP가 뭐지?"를 DNS 서버에 물어봐요. 답으로 IP 주소를 받아요.
2. **TCP 연결 (전송 계층)** — 받은 IP의 443번 포트로 3-웨이 핸드셰이크를 해서 연결을 맺어요.
3. **암호화 협상** — HTTPS니까 서버의 인증서를 확인하고, 이후 주고받을 내용을 암호화할 준비를 해요.
4. **HTTP 요청 전송** — `GET / HTTP/1.1` 요청을 보내요. 이 데이터는 아래 계층으로 내려가며 TCP 헤더, IP 헤더, 이더넷 헤더가 차례로 붙어요(캡슐화).
5. **라우팅 (네트워크 계층)** — 공유기 → 통신사 → 여러 라우터를 거쳐 목적지 서버까지 길을 찾아가요.
6. **서버 응답** — 서버가 `200 OK`와 함께 HTML을 보내요.
7. **화면 그리기** — 브라우저가 HTML을 읽으며 필요한 CSS·이미지·폰트를 **추가로 요청**하고, 다 모이면 화면에 그려요.

인터넷이 안 될 때 점검하는 순서도 이 흐름을 거꾸로 밟는 거예요. 랜선/와이파이 확인(1·2계층) → IP를 제대로 받았는지 확인(3계층) → 특정 사이트만 안 되는지 확인(7계층) 순서로요.

## 확인 문제

**문제 1.** IP 주소와 포트 번호는 각각 무엇을 찾는 데 쓰이나요? 그리고 이 둘은 OSI 몇 계층에 해당하나요?

<details>
<summary>정답 확인</summary>

**정답:** IP 주소는 **컴퓨터(장비)**를 찾는 데 쓰이며 **3계층(네트워크)**, 포트 번호는 그 컴퓨터 안의 **프로그램**을 구분하는 데 쓰이며 **4계층(전송)**입니다.

**해설:** 아파트로 치면 IP는 동 주소, 포트는 호수예요. 한 컴퓨터에서 브라우저와 게임이 동시에 통신해도 데이터가 섞이지 않는 것은 포트 번호로 구분하기 때문이에요.

</details>

**문제 2.** 다음 두 상황에는 TCP와 UDP 중 무엇이 더 알맞을까요? 이유도 함께 말해 보세요.

- (가) 100MB짜리 압축 파일을 내려받는다
- (나) 친구와 실시간 화상통화를 한다

<details>
<summary>정답 확인</summary>

**정답:** (가) TCP, (나) UDP

**해설:** 파일은 한 조각만 빠져도 열리지 않으므로 도착 확인과 재전송을 보장하는 **TCP**가 맞아요. 화상통화는 0.5초 전 화면을 다시 받아 봐야 이미 지나간 장면이라 쓸모가 없어요. 조금 끊기더라도 지연이 적은 **UDP**가 유리해요.

</details>

**문제 3.** 웹사이트에 접속했더니 `503`이 떴어요. 문제의 원인은 내 컴퓨터 쪽일까요, 서버 쪽일까요? 어떻게 판단했나요?

<details>
<summary>정답 확인</summary>

**정답:** 서버 쪽

**해설:** 상태 코드는 맨 앞자리로 성격을 구분해요. **4xx는 요청한 쪽(클라이언트)의 문제**, **5xx는 서버의 문제**예요. 503은 서버가 일시적으로 요청을 처리할 수 없다는 뜻이라 주소를 아무리 고쳐 써도 해결되지 않아요. 잠시 뒤 다시 시도하는 것이 맞습니다.

</details>

## 요약

- 네트워크를 **계층**으로 나누면 문제를 어느 층에서 찾을지 좁힐 수 있고, 한 층을 바꿔도 나머지를 그대로 쓸 수 있다.
- **OSI 7계층**은 물리 → 데이터 링크 → 네트워크 → 전송 → 세션 → 표현 → 응용 순이며, **TCP/IP 4계층**에서는 5·6·7이 응용으로, 1·2가 네트워크 접근으로 합쳐진다.
- **IP 주소는 컴퓨터**를, **포트는 그 안의 프로그램**을 가리킨다. 도메인 이름을 IP로 바꿔 주는 것이 DNS다.
- **TCP는 등기우편**(연결·확인·재전송), **UDP는 엽서**(빠르지만 보장 없음)로, 어느 쪽이 우월한 게 아니라 용도가 다르다.
- **HTTP**는 요청(메서드·경로·헤더)과 응답(상태 코드·헤더·본문)이 한 쌍으로 오간다. 상태 코드는 4xx가 요청 잘못, 5xx가 서버 잘못이다.
